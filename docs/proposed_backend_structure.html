    Proposed Architecture — Domain-First

    Today the backend is layer-first (app/models/, app/schemas/, app/routers/, app/services/) with partial domain sub-folders under each layer. That means anything related to (say) mutual funds is split across four folders, with a fifth (ai_bridge/) and a sixth (ingestion) attached at random.

    The proposal flips the tree: every domain owns its full vertical stack (models/ · schemas/ · routers/ · services/). Each domain folder is self-contained, the four sub-folders are identical in shape across every domain, and cross-cutting infra moves to core/.

    Why this scales

    • One place per feature. Add a new MF feature → all 4 files land in domains/mutual_funds/. No more grep-across-the-tree.
    • Consistent shape. Every domain has exactly the same four sub-folders, even when one is sparse — predictable for new joiners.
    • Clear ownership. A team can own a domain folder end-to-end; tests live alongside each layer.
    • Renames for clarity. e.g. mf/ → mutual_funds/, stocks/ → equities/, ai_bridge/ → ai_engine/, chat_core/ → chat_orchestrator/.
    • DB-level: explicit family naming. Every table gets a domain prefix (already true for mf_* · cashflow_* · rebalancing_*; extend to profile_* · goal_* · chat_* · equity_*).

    This page is a shallow design copy: it shows the new folder shape and the function signatures / class skeletons that should live in each file. No code is moved or executed. If you approve, the next step is the actual refactor (one domain at a time, behind a feature-test pass).

    Domain-First Overview

    The repository's app/ package is reorganised into three top-level groups:

    1. core/ — Cross-cutting infrastructure

    Anything that doesn't belong to one specific business domain: config, the SQLAlchemy base + session factory, FastAPI dependencies (auth, effective-user), security helpers, and centralised exception handlers.

    2. domains/ — Business domains (the bulk of the app)

    Each domain folder has the same four sub-folders:

    domains/<family>/
    models/      # SQLAlchemy ORM tables for this family
    schemas/    # Pydantic request/response shapes
    routers/    # FastAPI HTTP endpoints (one file per resource)
    services/   # Business logic (DB queries, pure functions, ingest)

    Domains:

    • identity — user, auth, OTP, family members, linked accounts, onboarding
    • profile — risk, tax, investment, personal finance, constraints, properties, other assets, review prefs
    • goals — financial goals, contributions, holdings
    • portfolio — portfolio + allocations + holdings + history + NAV history
    • mutual_funds — MF metadata, NAV, txns, SIPs, snapshots, watchlists, AA imports, mfapi.in
    • equities — stocks: company metadata, prices, transactions
    • asset_allocation — allocation runs, buckets, aggregates, targets
    • rebalancing — rebalancing runs, trades, warnings, fund rows, subgroup summaries
    • cashflow — cashflow plan engine: assumptions, one-off events, plan runs, headlines
    • ingestion — CAMS-CAS PDF, SimBanks, Finvu (legacy) — all ingest adapters
    • advisory — IPS, meeting notes, discovery helpers
    • notifications — notification records and delivery
    • chat — chat sessions, messages, per-session state, AI module run telemetry
    • ai_engine — bridges to AI_Agents (chat orchestrator, intent router, per-agent bridges, answer formatter, visualizations)

    3. routers/__init__.py — Router aggregator

    Stays at app/routers/__init__.py and just collects every domain's routers/__init__.py's router exports. main.py imports all_routers from there — same as today.

    Conventions enforced by this layout

    • Naming: every router file ends with _router.py; every service file ends with _service.py (only when its main responsibility is a service — pure helpers like paging.py keep their own name).
    • Family prefixes on DB tables: profile_*, goal_*, chat_*, equity_*, portfolio_*, etc. Already-prefixed tables (mf_*, cashflow_*, rebalancing_*) stay.
    • One model per file for new tables. (Existing aggregations like rebalancing/rebalancing_run.py are fine.)
    • Per-domain __init__.py re-exports the family's public names so consumers write from app.domains.mutual_funds.models import MfTransaction rather than poking at the inner file.
    • Tests live next to code: domains/<family>/services/tests/.

    Chat Flow — end-to-end trigger sequence

    This walks through exactly what happens when a user types a message into the chat, which files are touched, in what order, and where each piece of state lands.

    Entry point

    POST /api/v1/chat/sessions/{session_id}/send
   └─ app/domains/chat/routers/chat_router.py :: send()
      ├─ resolves user via core/dependencies.get_ai_user_context  (eager-loads User graph)
      ├─ instantiates ChatBrain(db, user)
      └─ awaits brain.run_turn(session_id, payload)

    Inside ChatBrain.run_turn (the orchestrator)

    File: app/domains/ai_engine/services/chat_orchestrator/brain.py

    async def run_turn(session_id, payload):
    # 1. Build a TurnContext — the bag of state every downstream module reads from.
    ctx = TurnContext(
        db=self.db,
        user=self.user,                  # User w/ eager-loaded relations
        session=load_session(db, id),    # ChatSession ORM row
        session_state=load_state(...),   # ChatSessionState (cross-turn gates)
        history=await chat_context_service.load_history(db, session),
        user_text=payload.text,
    )

    # 2. Persist the user message immediately so we never lose it on a crash.
    await chat_session_service.append_message(db, session, role="user", content=payload.text)

    # 3. Classify intent. Reads the last N messages + the new user_text.
    intent = await intent_classifier_bridge.classify(ctx)
    # intent = { name: "asset_allocation" | "rebalancing" | "goal_planning"
    #                 | "market_commentary" | "portfolio_query" | "general_chat",
    #           confidence: 0.0-1.0, slots: {...} }

    # 4. Telemetry row — captures "we picked intent X for turn Y".
    run_id = await chat_telemetry_service.start_run(db, session, intent)

    # 5. Dispatch to the matching bridge via intent_router.dispatch(ctx, intent).
    #    Each bridge returns a BranchResult { text, persisted_refs, charts, side_effects }.
    branch = await intent_router.dispatch(ctx, intent)

    # 6. Shape the chat reply (text + chart specs + suggested actions).
    reply = answer_formatter.render(branch.text, charts=branch.charts)

    # 7. Persist the assistant reply and close out telemetry.
    await chat_session_service.append_message(db, session, role="assistant", content=reply.text)
    await chat_telemetry_service.finish_run(db, run_id, branch)

    # 8. Optional gate flip for multi-turn flows (e.g., goal_planning awaiting_save).
    if branch.side_effects.get("awaiting_save"):
        await chat_session_service.update_state(db, session, awaiting_save=True)

    return reply

    The dispatch table (the "switch")

    File: app/domains/ai_engine/services/intent_router/intent_router.py

    from app.domains.ai_engine.services import (
    asset_allocation_bridge,
    rebalancing_bridge,
    goal_planning_bridge,
    market_commentary_bridge,
    portfolio_query_bridge,
    general_chat_bridge,
)

# Single source of truth: intent name → bridge entry point.
_DISPATCH = {
    "asset_allocation":  asset_allocation_bridge.service.run,
    "rebalancing":       rebalancing_bridge.service.run,
    "goal_planning":     goal_planning_bridge.service.run,
    "market_commentary": market_commentary_bridge.service.get_commentary,
    "portfolio_query":   portfolio_query_bridge.service.answer,
    "general_chat":      general_chat_bridge.service.respond,
}

async def dispatch(ctx, intent) -> BranchResult:
    # Multi-turn gate check — if the previous turn opened a save flow,
    # keep routing to goal_planning regardless of the new intent until resolved.
    if ctx.session_state.awaiting_save:
        return await goal_planning_bridge.service.run(ctx, resume=True)

    handler = _DISPATCH.get(intent.name, general_chat_bridge.service.respond)
    return await handler(ctx)

    Inside a bridge — same shape every time

    Every bridge follows the same five steps. Example: asset_allocation_bridge.

    async def run(ctx) -> BranchResult:
    # (a) Build the AI_Agents input from ORM data (risk profile, goals, holdings, etc.)
    input_dto = input_builder.build(ctx.user)

    # (b) Call the AI_Agents orchestrator (LangChain + Anthropic under the hood).
    raw_output = await AI_Agents.asset_allocation_pydantic.run(input_dto)

    # (c) Apply user overrides (caps/floors, hard exclusions, ESG, …).
    final_output = overrides.apply(raw_output, ctx.user)

    # (d) PERSIST. Write a new asset_allocation_run + buckets + targets via
    #     domains.asset_allocation.services.allocation_persist_service.write_run().
    run_row = await allocation_persist_service.write_run(ctx.db, ctx.user, final_output)

    # (e) Shape the chat reply: markdown tables + chart specs.
    text = allocation_tables_md.render(final_output)
    charts = [visualizations.registry.build("category_gap_bar", final_output)]
    return BranchResult(text=text, charts=charts, persisted_refs={"allocation_run_id": run_row.id})

    How each intent fans out

    IntentBridgeCalls (AI_Agents)Persists toChart(s)
    asset_allocation asset_allocation_bridge asset_allocation_pydantic asset_allocation_runs + buckets/targets via allocation_persist_service category_gap_bar
    rebalancing rebalancing_bridge Rebalancing (uses latest cached allocation as baseline) rebalancing_runs + trades/warnings via rebalancing_persist_service trade summary
    goal_planning goal_planning_bridge cashflow_statement + counterfactuals cashflow_plan_runs via cashflow_persist_service; opens awaiting_save gate cashflow timeline
    market_commentary market_commentary_bridge market_commentary nothing (read-only) — telemetry row only none
    portfolio_query portfolio_query_bridge portfolio_query nothing (read-only); reads MF + portfolio + equities tables varies (donut, holdings table)
    general_chat general_chat_bridge direct ChatAnthropic via LangChain nothingnone

    State written every turn (always)

    1. One chat_messages row for the user message (saved before classification — so a crash mid-pipeline still leaves the question on record).
    2. One chat_ai_module_runs row opened at start of dispatch and closed at end. Records intent, branch, latency, token counts, success/error.
    3. One chat_messages row for the assistant reply (after the branch returns).
    4. (Optional) chat_session_states upsert if the branch flipped a gate (e.g., awaiting_save) — read by the next turn's dispatcher.
    5. (Optional) domain rows written by the bridge: an allocation run, a rebalancing run, a cashflow plan run, etc. The persistence is owned by the matching domain's *_persist_service — bridges never touch ORM directly.
    Why this layering matters. Bridges depend on domain persistence services (one direction). Domain services never import bridges (no cycle). The chat orchestrator only knows about intents, not about agents — adding a new agent means adding a new bridge folder + one line in _DISPATCH, with no edits to the brain.

    Multi-turn flows (the awaiting_save example)

    Goal planning produces a counterfactual ("what if we increase monthly contributions by ₹5k?"). The bridge writes a candidate plan run and flips awaiting_save=true in chat_session_state. The next user turn — regardless of its content — is routed back to goal_planning_bridge with resume=True, which interprets it as a "yes save / no discard" answer. This is the only place the dispatch table is bypassed.

    Error path

    try:
    branch = await intent_router.dispatch(ctx, intent)
except AgentTimeoutError as e:
    await chat_telemetry_service.fail_run(db, run_id, error="timeout")
    reply = answer_formatter.render_error("I'm taking longer than usual — try again in a sec.")
except AgentValidationError as e:
    await chat_telemetry_service.fail_run(db, run_id, error=str(e))
    reply = answer_formatter.render_error("I couldn't parse my own answer; please rephrase.")
except Exception as e:                                # last-resort
    await chat_telemetry_service.fail_run(db, run_id, error=repr(e))
    raise                                              # bubble to FastAPI handler -> 500

    The user message is already persisted by step 2 above, and the telemetry row carries the failure mode, so nothing is lost on the way down.

    Migration strategy. Renaming Python modules is cheap; renaming DB tables is a migration. Recommendation:
    1. Phase 1 (Python only): move files under app/domains/<family>/, keep table names. One PR per domain, fixed by import-rewrite + test run.
    2. Phase 2 (DB renames, opt-in): only the tables where the current name is genuinely confusing (e.g. risk_profiles vs the AI domain's risk profiling). Each as its own Alembic migration with a no-op read-side compatibility view if needed.
