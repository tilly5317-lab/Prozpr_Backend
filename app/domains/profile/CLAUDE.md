# app/domains/profile/ — risk / tax / investment / constraints / personal finance / properties / review prefs / effective-risk merge / standing investment preferences

## Layers

- **models/** — one ORM model per profile section (risk, tax, investment + its constraints, personal finance, other investments, property, review preference, effective-risk assessment).
- **schemas/** — per-section payloads + a `FullProfileResponse` aggregator.
- **routers/** — one `/profile` router with per-section PATCH endpoints.
- **services/** — `profile_finance.py` (household-finance scalar resolver) + `personal_finance_write_service.py` (its commit-free write counterpart, so a domain owning a *derived* view of a canonical field can update it without reaching into `personal_finance_profiles`) + `_effective_risk/` + the investment-preference trio: `preference_save_service.py` (the single WRITE path, for both the screen and chat), `preference_view.py` (the single READ path — see Gotchas), `preference_lexicon.py` (the word→facet table chat extraction maps `PreferenceAsk` through), `screen_preference_service.py` (the percentage screen's translation layer) and `preference_tagging.py` (run-level preference provenance, used by every engine that persists a run).

## Gotchas & invariants

- `profile_finance.py` is the SINGLE source of truth for household-finance scalars (income, expenses, assets/liabilities, tax rate, properties). Every engine and the IPS view reads them through its `*_pfp` helpers, sourced from `personal_finance_profiles` — never off `investment_profile` columns, which were slimmed down (`services/profile_finance.py`).
- `_effective_risk/` is the effective-risk calc, not a generic service. `merge.py` recalculates *incrementally*: a trigger (e.g. `risk_profile_update`) carries only its own input keys and everything else is carried forward from the last stored assessment — except `age`, which is ALWAYS re-derived from date of birth (`_ALWAYS_REFRESH`), so the age-only triggers (`portfolio_allocation_update`, `finvu_portfolio_sync`, `simbanks_sync`, `birthday`, `scheduled`) can shift the score with no profile section touched; `manual` or an unrecognized trigger falls back to a full refresh from DB, and calculations + output are always recomputed (`services/_effective_risk/merge.py:22-45`).
- `saved_investment_preferences` rows freeze at activation. A candidate (`activated_at` NULL) may have its target pcts / `shortfall_reason` filled after its engine run; once active, the ONLY permitted write is `is_active → false`. Both save paths deactivate the prior row and `flush()` BEFORE activating the new one — the partial unique index (`uq_saved_investment_preferences_active_user`, at most one active row per user) trips otherwise. `supersedes_id` is set once, at activation, on the new row; never write the replaced row (`services/preference_save_service.py::_persist_confirm`, `::confirm_candidate`).
- **`customer_choices` has TWO shapes and exactly ONE reader** (`services/preference_view.py::canonical_intent`). Chat writes `{asset_class, subgroups}`, the screen `{class_mix, pins}`; readers that understood only their own shape are why a chat what-if once discarded a screen-saved preference entirely. NOTE (2026-09-17): with chat what-ifs retired, `canonical_intent` has no live caller — it stays with the one-off chain as the re-enable seam. Chat-shaped rows pass through UNTOUCHED — their relative tokens are what `_changed_intent`'s anti-ratchet compares; anything else derives from the TYPED columns. The two idempotence checks (`::confirm_candidate`, `screen_preference_service.py:208`) compare the raw column on purpose: they ask "did this surface re-send its own payload".
- **Outside this domain, read a preference via `preference_view.active_preferences_for`, never the relationship** (`describe_active` was removed 2026-09-17 with the readout) — `tests/test_saved_investment_preferences.py::test_contract_single_computation_reader` guards it, GREEN since 2026-09-19. Its two checks differ in strictness on purpose: the **relationship** read is the computation-time one that would put a DB fetch inside an engine, so its allow-list stays tight (`profile/`, `identity/`, `core/`, `paa_engine/input_builder.py`, `aa_engine/service.py`); a **model import** for a read-only join off a run's FK is the designed way to recover what shaped a run, so it may be sanctioned with a reason. Known hole: the relationship check greps a literal `.saved_investment_preference`, so a `getattr` form still slips through silently.
- The preferences screen speaks a COMPLETE distribution (2026-09-15). Pins arrive one per settable category with blanks as explicit `0`, and `0` is a hard EXCLUSION the engine honours — while an OMITTED row still means "engine decides"; never collapse the two. `multi_asset` is validated against all three class bars at the engine's own 65/25/10 composition, not wholly as equity — the recommended sleeve is routinely ~half the portfolio, so charging it to equity alone rejected the screen's own recommendation (`services/screen_preference_service.py::_class_budget_consumed`).
- **The GET's `current` block is today's holdings in the screen's rows, and it excludes MORE than the caption names** (`services/screen_preference_service.py::current_block`, frontend spec 2026-09-20 §3.1). It is built from the lump-sum path's `HoldingsSnapshot` (canonical classifier over `PortfolioHolding.current_value`) — never a second holdings query. `holdings` is each settable row's share of the SETTABLE part and sums to 100; `excluded_pct` is everything else as a share of the whole: the frozen rows (ELSS, direct stock) the frontend caption names, PLUS held categories the screen cannot set (dividend yield, silver, China) and unclassified value (decision 2026-09-26 — dropping those instead inflates every settable row and reports nothing excluded). A failed snapshot read logs a WARNING and sends `current: null`; the screen shows no today bar and the rest of the GET still arrives.
