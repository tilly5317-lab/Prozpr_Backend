# app/domains/rebalancing/ — rebalancing runs, trades, fund rows, subgroup summaries, warnings

## Entry / contract
- `rebalancing_module_service` is the gateway on the chat path — the brain calls its `run(turn, ctx, prior)`. One other live caller bypasses it: the debug / frontend-driven route `POST /api/v1/ai-modules/rebalancing/compute` (`app/domains/ai_engine/routers/rebalancing_router.py`) calls `rebal_engine.service.compute_rebalancing_result` directly and commits the session itself. The AI bridge that *produces* the source allocation lives in `app/domains/ai_engine`. The source allocation a run rebalances toward is the latest `AssetAllocationRun` (plus its IDEAL `PortfolioAllocationSnapshot`) written by the `asset_allocation` domain, read cache-first with a 90-day TTL and, on a miss, recomputed inline via `asset_allocation`'s `aa_engine.compute_allocation_result` — nothing in `app/domains/ai_engine` produces it.

## Layers
- **models/** — `RebalancingRun` and its children `RebalancingTrade` / `RebalancingFundRow` / `RebalancingSubgroupSummary` / `RebalancingWarning`.
- **schemas/** — the run-API contract (pydantic views over the run tables) in `__init__.py` — including the read-time computed `summary` and `asset_class_breakdown` — plus `readiness` (payload for `GET /rebalancing/readiness`).
- **routers/** — the `/rebalancing` router.
- **services/** — `rebalancing_persist_service` (the write surface, called at the end of a run by `rebal_engine/service.py`); `rebalancing_read_service` (read-side helper over persisted runs — `additional_investment`'s SIP path mirrors the latest run's BUY trades through it); `rebalancing_module_service` (the gateway above); `rebalancing_summary.py` (pure, DB-free headline — title/subtitle/reason — behind the run-detail `summary` computed field); `asset_class_breakdown.py` (THE current-vs-target-vs-goal Equity/Debt/Others rollup — `asset_class_mix_from_rows`, shared by the Invest-page bars AND the rebalancing chat facts pack, see Gotchas); `plan_gap.py` (pure: the ₹ the short-term rule locks, and the one-line why the plan stops short of the goal mix); `rebal_engine/` — the compute engine, documented in its own `rebal_engine/CLAUDE.md`.

## Gotchas & invariants
- **One asset-class rollup, two surfaces** — `asset_class_mix_from_rows` (`services/asset_class_breakdown.py`) feeds both the Invest bars and the chat facts pack; separate rollups once reported 98/1/0 vs 95/3/2 for the same holdings. CURRENT and TARGET both look each row through on its own `sub_category`. The 65/25/10 `multi_asset` sleeve split now applies ONLY where a row has no fund identity — a subgroup total (the GOAL mix, the legacy no-fund-rows fallback) or an individual row whose `sub_category` never resolved. It used to apply to the whole TARGET column, which re-labelled money the plan never traded: a Flexi Cap fund and an Aggressive Hybrid held inside `multi_asset` read honestly on Current and 65/25/10 on Target, inventing ~11pp of Debt and ~4pp of Others on a plan that could sell neither (2026-09-27).
- **Three bars, not two: `target` ≠ the customer's preference.** `RebalancingAssetClassBreakdown` ships `goal_inr` per row (from `goal_target_inr` — goals + risk + saved preference) alongside `target_inr` (where THIS PLAN lands), plus `short_term_locked_inr` and `gap` — one amber line the page shows collapsed (it carries both percentages, so it answers *what*) over a summary/points/footnote it reveals on tap (the *why*). A paragraph parked under a chart goes unread; the copy lives in `plan_gap.py`, never the component. They legitimately differ because a rebalance is cash-neutral and **optional trims are long-term-only** — so a portfolio 84% under a year old can move ~16% of itself no matter how far off the goal it sits, and the whole buy budget is whatever the sells raised. `services/plan_gap.py` builds the note off `rebalancing_fund_rows.pass2_undersell_amount`, the engine's own record of rupees it wanted to sell and could not. Shipping only Current + Target is what made customers who had saved 50/50 read a 77/20 Target bar as a broken preference. The named class is the furthest-off one, tie-broken by a canonical Equity/Debt/Others order — a two-class portfolio's gaps are always equal and opposite, and set iteration made one plan word itself two ways across server processes.
- **Per-fund target is `present + buys − sells`, never `final_target_amount`** — that column is a per-candidate uncapped target and sums ~30% above the portfolio (`plan_rows_from_run`).
- **The pack ships current AND target AND ideal.** With only current present, the formatter answered "what is the plan moving me toward?" by citing it, then invented lock-ins to explain the mismatch (`rebal_engine/service.py` `build_rebal_facts_pack`).
- A run ALWAYS rebalances toward a persisted asset-allocation run — `source_allocation_run_id` is required (`services/rebalancing_persist_service.py`).
- The engine reuses a cached allocation for up to 90 days (`ALLOCATION_TTL_DAYS`); a chat override such as `additional_cash_inr` sets `force_fresh_allocation=True`, which skips that cache and re-runs allocation inline (`rebal_engine/service.py`). Miss this and chat returns a stale plan.
- **Preferences reach the engine as a SAVED row, never as a rebalancing override.** The shared PAA input builder loads the active `saved_investment_preference` into `human_override` (`paa_engine/input_builder.py`), so every plan honours it with no chat involvement. The old chat channel (`preference_asks` → `build_intent` → `resolve_one_off` → `chat_overrides["human_override_preferences"]`) is retired — see the no-what-if bullet below.
- **`active_preferences` and `constraint_impact` are mutually exclusive** (`rebal_engine/service.py::build_rebal_facts_pack` uses `elif`). The first says a SAVED preference shaped this plan, the second is an unsaved candidate with its own save offer; both at once credits a save never made. The chat seam also suppresses it on `counterfactual_explore` (no disclosure rule exists for that mode), and narrate/educate resolves the row from the RUN's FK rather than the active row, so a newer preference is never credited for an older plan (`chat.py::_preference_row_for_turn`).
- **Chat runs NO preference what-if (ruling 2026-09-17).** Every preference-shaped ask — exposure ("more equity"), readout, change, undo — points at the preferences page with `show_preferences_pill=True` and reshapes nothing. The pointer rides the FACTS PACK as `preference_pointer` so `answer_formatter` writes it — never string-concatenated onto the reply. A MIXED ask keeps its servable half: a first turn still computes the plan, and a tax/cash override still runs `_counterfactual_explore`, each closing with the pointer. Every redirect emits a `redirected_to_preferences` token, so demand for chat-side changes is measurable. The detector still EXTRACTS `preference_asks`, which keeps the seam usable. `_handle_preference_what_if` and its candidate-row machinery are UNREFERENCED but deliberately intact — chat-side changes are planned; call it from `_handle_action` to re-enable. `POST /{run_id}/save` still saves the plan; its `activate_candidate_for_run` call is now a no-op because no candidate is ever written.
- **Unserved asks emit tokens only.** `preference_unserved` carries a fixed `failure_class` and ids, never chat text (`app/core/observability.py`).
- **A first-message preference ask is MIXED intent: it gets the plan AND the pointer.** `handle` still detects first (the brain's speculative detect if present, else the serial `_detect_rebal_action(None, ctx)`), but since 2026-09-17 the plain plan IS computed and `PREFERENCE_REDIRECT_MESSAGE` is appended, with the pill set — "rebalance me, but more equity" wants a plan, and withholding it to show only a pointer would be worse (`rebal_engine/chat.py`).
