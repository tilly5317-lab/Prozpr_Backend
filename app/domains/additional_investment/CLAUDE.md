# app/domains/additional_investment/ — deploy fresh money (lumpsum/SIP) into specific funds to BUY

## Entry / contract
- `additional_investment_module_service` is the ONLY gateway to the additional-investment AI module — the brain calls its `run(turn, ctx, prior)`. The pure engine that picks the funds lives in `AI_Agents/src/additional_investment` (`run_additional_investment`) and is reached only through this domain. The source practical allocation is re-computed inside `ainv_engine/service.py` (via `compute_practical_allocation_result`) and persisted to yield `source_allocation_run_id`; for lumpsum it is pinned to actual holdings + fresh money via `CorpusPin`.

## Layers
- **models/** — `AdditionalInvestmentRun` (table `additional_investment_runs`) and its children `AdditionalInvestmentTarget` / `AdditionalInvestmentBuy`.
- **schemas/** — HTTP contract (`__init__.py`). SIP: `SipPlanResponse` + `SipFundBuy` (the flat per-fund monthly view the Invest page reads) and `SipCreateRequest` (`monthly_amount_inr` — the only client-supplied field on create); `SipPlanResponse` also carries `goal_plan_monthly_investment_inr` + `goal_plan_in_sync` — the goal-planning SIP comparison that drives the Invest-page "sync your goal plan?" nudge. Lumpsum: `LumpsumCreateRequest` (`amount_inr` + `action` — only `add` supported) / `LumpsumPlanResponse` + `LumpsumFundBuy` (per-fund one-time amount + `reason`) + `LumpsumAlignmentRow` (per-part ideal/current/gap/deploy — the "why these funds" section) + `headline_reason`.
- **services/** — `additional_investment_module_service` (the gateway above); `additional_investment_persist_service` (the normalized BUY-only write surface); `additional_investment_read_service` (`get_latest_sip_plan` — latest `sip_monthly` run reshaped; `get_latest_lumpsum_plan` — latest `lumpsum` run with reasoning rebuilt from persisted deficit facts); `additional_investment_create_service` (`create_sip_plan_for_user`) and `additional_investment_lumpsum_create_service` (`create_lumpsum_plan_for_user` — same chat compute path from the Invest page, `cadence=lumpsum`, no chat session, `action!='add'` → 422); `lumpsum_reasoning.py` (pure, deterministic: subgroup labels + per-fund `reason` + alignment rows + headline from the engine's own deficit facts / target bucket — NOT an LLM); `ainv_engine/` — the compute orchestration (named `ainv_engine` because `ai_engine` is taken): `service.py` (outcome assembly), `input_builder.py` (engine input, `deficit_mode` switch), `holdings_snapshot.py` (current holdings by subgroup), `category.py` (category resolution + status), `chat.py` (chat handler: extractor + formatter bodies).
- **routers/** — `additional_investment_router` exposes `GET`/`POST /additional-investment/sip` (latest monthly SIP plan / set up a SIP for a per-month amount) and `GET`/`POST /additional-investment/lumpsum` (latest one-time lumpsum plan with reasoning / plan a lumpsum for a one-time amount). Both are Invest-page create paths; chat can still produce runs too; all write to the same tables.

## Gotchas & invariants
- **Import `chat` lazily.** `ainv_engine/__init__.py` is docstring-only and must NOT re-export `chat` — eager import triggers a circular import via `chat_core.turn_context` (mirrors `rebal_engine`). The `@register("additional_investment")` side-effect is landed by a lazy `from ...ainv_engine import chat` inside `additional_investment_module_service.run`.
- **The deploy-request LLM extracts amount + cadence + optional category.** Each turn `ainv_engine/chat.py` runs a Haiku `classify_action` call on a dedicated key (`get_anthropic_additional_investment_key()`) pulling deploy amount, lumpsum/SIP cadence, and `focus_category`, falling back to the deterministic `parse_deploy_request` regex on failure (`ainv_engine/chat.py`).
- **Lumpsum runs deficit-fill against real holdings** (`ainv_engine/service.py`, `AINV_ENGINE_VERSION = "ainv-3.2.0"`). One `HoldingsSnapshot` supplies both the `CorpusPin` that pins PAA at holdings + deploy (total/MF/non-MF-equity/ELSS corpus) and the engine's `current_value_by_subgroup`; per-subgroup ideal/current/gap/buy facts surface as `outcome.deficit_facts` for the formatter. SIP keeps the legacy profile-corpus path. No snapshot fallback by product decision (CAMS upload mandatory) — a snapshot failure propagates.
- **Lumpsum reasoning is deterministic, built from the engine's own facts** — no new AI module. `deficit_facts` are persisted into the run's `request_input` JSONB (`service.py`, keyed `deficit_facts`) so the READ endpoint rebuilds the same per-fund `reason` + alignment section the create path returns (`lumpsum_reasoning.py`). The engine's canned `FundBuy.reason` is ignored on this surface. Legacy lumpsum runs (persisted before this) have no `deficit_facts` → reasoning degrades to a rank/category line, alignment section omitted.
- **Lumpsum never syncs the canonical SIP.** A lumpsum is a one-off, so `starting_monthly_investment` is untouched (the adapter only syncs on `sip_monthly`); the lumpsum read shape carries no goal-plan-sync fields.
- **SIP mirrors the latest rebalancing run** (spec 2026-07-05). `ainv_engine/service.py` reads BUY ISINs via `rebalancing_read_service.latest_buy_trades_by_subgroup` (acting user; run status ignored — product call: all plans treated as accepted); enhancement never gate — a read failure logs and degrades to the engine's rank-1 fallback, never blocks the reply. `sip_rebal_run_id` (str, never raw UUID — JSONB json.dumps) lands in `request_extras` only when a run actually sourced funds. **That fallback is holdings-blind and fires more often since engine 1.3.0** — the rank-band change cuts BUY trades, so `latest_buy_trades_by_subgroup` returns a thinner map and more sleeves drop to rank-1 (`AI_Agents/src/additional_investment/selection.py`, Stage 2). Consequence: a customer whose rank-2 holding the rebalancer deliberately protected can still accrete a fresh rank-1 position beside it. Graceful and per-sleeve, but a known product inconsistency — making SIP selection holdings-aware is an open design task.
- **A category ask adds a facts block, not a route** (`ainv_engine/category.py`). `resolve_category` canonicalises the customer's words against the ranking's actual `sub_category` values; `top_funds_for_category` + `category_status` build the `category_ask` facts block the formatter narrates per status — the status vocabulary is contractual.
- **BUY-only, write-once.** A run only adds new money; no sell/status lifecycle, no update-status route (contrast `RebalancingRun.status`) (`services/additional_investment_persist_service.py`). "Adjusting" a SIP from the Invest page just computes a NEW run — the read side always returns the latest `sip_monthly` run.
- **Goal-plan sync is compared here, written elsewhere.** The read service reads `personal_finance_profiles.starting_monthly_investment` (via `profile_finance.starting_monthly_investment_pfp`) to set `goal_plan_in_sync`. The actual "update everywhere" write goes through the profile domain's `PUT /profile/personal-finance` (the SSOT the cashflow/goal engine reads) — this domain never writes PFP (`additional_investment_read_service.py`).
- **The Invest-page create reuses the chat compute path without a chat session** (`additional_investment_create_service`). It wraps the AI `User` graph in a minimal `TurnContext` (compute reads only `user_ctx` + `chat_overrides=None`) and calls `compute_additional_investment_result(..., chat_session_id=None, persist=True)`. The persist gate is `if persist:` (NOT `and chat_session_id is not None`) so a null session still writes — the run's `chat_session_id` FK is nullable (`ainv_engine/service.py`). The create service owns the commit and re-reads via `get_latest_sip_plan`.
- **Money is `float`, not `Decimal`.** This domain follows the allocation family (`practical_asset_allocation`), not Rebalancing — floats flow straight into `Numeric(18,2)`; do NOT import `_to_decimal` in the persist service (`services/additional_investment_persist_service.py`).
- A run always deploys against the persisted practical-allocation run it was derived from — `source_allocation_run_id` (FK to `practical_asset_allocation_runs.id`) is required (`services/additional_investment_persist_service.py`).
