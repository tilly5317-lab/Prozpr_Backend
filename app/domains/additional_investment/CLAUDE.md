# app/domains/additional_investment/ — deploy fresh money (lumpsum/SIP) into specific funds to BUY

## Entry / contract
- `additional_investment_module_service` is the ONLY gateway — the brain calls its `run(turn, ctx, prior)`. The fund-picking engine lives in `AI_Agents/src/additional_investment` (`run_additional_investment`), reached only through this domain. `ainv_engine/service.py` re-computes + persists the source practical allocation to yield the required `source_allocation_run_id` FK (to `practical_asset_allocation_runs.id`); for lumpsum it pins PAA to holdings + fresh money via `CorpusPin`.

## Layers
- **models/** — `AdditionalInvestmentRun` (table `additional_investment_runs`) + children `AdditionalInvestmentTarget`/`AdditionalInvestmentBuy`.
- **schemas/** — HTTP contract. SIP (`SipPlanResponse`/`SipFundBuy`/`SipCreateRequest`, only `monthly_amount_inr` client-supplied) also carries `goal_plan_monthly_investment_inr` + `goal_plan_in_sync` — the Invest-page "sync your goal plan?" nudge. Lumpsum (`LumpsumCreateRequest` — `action` only `add`, else 422 / `LumpsumPlanResponse` + per-fund `LumpsumFundBuy` + per-part `LumpsumAlignmentRow` + `headline_reason`).
- **services/** — `_persist_service` (BUY-only write surface), `_read_service` (`get_latest_sip_plan`/`get_latest_lumpsum_plan`), `_create_service`/`_lumpsum_create_service` (Invest-page create, same compute path, no chat session), `lumpsum_reasoning.py` (deterministic reasoning, no LLM), and `ainv_engine/` — the compute orchestration (`service.py` outcome assembly, `input_builder.py`, `holdings_snapshot.py`, `category.py`, `chat.py` handler).
- **routers/** — `GET`/`POST /additional-investment/sip` and `/lumpsum` (latest plan / create for a monthly or one-time amount). Both are Invest-page create paths; chat also produces runs; all write the same tables.

## Gotchas & invariants
- **Import `chat` lazily.** `ainv_engine/__init__.py` is docstring-only and must NOT re-export `chat` — eager import triggers a circular import via `chat_core.turn_context` (mirrors `rebal_engine`). `additional_investment_module_service.run` lands the `@register("additional_investment")` side-effect with a lazy `from ...ainv_engine import chat`.
- **Deploy-request extraction runs on a dedicated key.** Each turn `ainv_engine/chat.py` runs a Haiku `classify_action` (`get_anthropic_additional_investment_key()`) pulling amount + lumpsum/SIP cadence + optional `focus_category`, falling back to the deterministic `parse_deploy_request` regex.
- **Clarify asks the AMOUNT ONLY (never lumpsum-vs-SIP); `compute` replies lead with WHERE THE MONEY GOES, not the amount** (`ainv_engine/chat.py`). Cadence is extracted when volunteered but a one-time deployment is assumed; echoing back the number the customer just gave reads as filler.
- **Lumpsum runs deficit-fill against real holdings** (`ainv_engine/service.py`, `AINV_ENGINE_VERSION = "ainv-3.2.0"`). One `HoldingsSnapshot` supplies both the `CorpusPin` and `current_value_by_subgroup`; per-subgroup ideal/current/gap/buy surface as `outcome.deficit_facts`. SIP keeps the legacy profile-corpus path. No snapshot fallback (CAMS upload mandatory) — a snapshot failure propagates.
- **Lumpsum reasoning is deterministic, from the engine's own facts.** `deficit_facts` are persisted into the run's `request_input` JSONB so the READ endpoint rebuilds the same per-fund `reason` + alignment section the create path returns (`lumpsum_reasoning.py`); the engine's canned `FundBuy.reason` is ignored. Legacy runs lacking `deficit_facts` degrade to a rank/category line. A lumpsum never syncs the canonical SIP (`starting_monthly_investment` untouched).
- **SIP mirrors the latest rebalancing run's BUY ISINs** via `rebalancing_read_service.latest_buy_trades_by_subgroup` (acting user, status ignored — all plans treated as accepted); a read failure degrades to the engine's rank-1 fallback and never blocks. `sip_rebal_run_id` is recorded only when a run sourced funds. **That fallback is holdings-blind and fires more since engine 1.3.0** (the rank-band change thins the BUY map), so a customer can accrete a fresh rank-1 beside a rank-2 holding the rebalancer deliberately protected — making SIP selection holdings-aware is open.
- **A category ask adds a facts block, not a route** (`ainv_engine/category.py`). `resolve_category` canonicalises the customer's words against the ranking's `sub_category` values; `category_status` builds the block the formatter narrates per status — the status vocabulary is contractual.
- **BUY-only, write-once.** A run only adds money — no sell/status lifecycle, no update-status route (contrast `RebalancingRun.status`). "Adjusting" a SIP just computes a NEW run; the read side always returns the latest `sip_monthly` run.
- **Goal-plan sync is compared here, written elsewhere.** The read service reads `personal_finance_profiles.starting_monthly_investment` to set `goal_plan_in_sync`, but the "update everywhere" write goes through the profile domain's `PUT /profile/personal-finance` — this domain never writes PFP (`additional_investment_read_service.py`).
- **The Invest-page create reuses the chat compute path without a chat session** (`additional_investment_create_service`). It wraps the AI `User` in a minimal `TurnContext` and calls `compute_additional_investment_result(..., chat_session_id=None, persist=True)`; the gate is `if persist:` (NOT session-gated), so a null session still writes — the run's `chat_session_id` FK is nullable.
- **Money is `float`, not `Decimal`.** This domain follows the allocation family (`practical_asset_allocation`); floats flow straight into `Numeric(18,2)` — do NOT import `_to_decimal` in the persist service.
