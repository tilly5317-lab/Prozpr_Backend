# app/domains/portfolio/ — portfolio container, allocations, holdings, history, net-worth series

## Layers

- **models/** — `Portfolio` (+ `PortfolioAllocation` / `PortfolioHolding` / `PortfolioHistory` in one file); `UserPortfolioNavHistory` (the daily net-worth series), `UserNetworthSeriesState` (one summary row per user), `UserSchemePosition` (materialised per-(user, scheme) end state), `PortfolioNetworthJob` (rebuild lifecycle row the UI polls).
- **schemas/** — portfolio + history/nav-history/TWR payloads.
- **routers/** — `/portfolio` (detail, allocations, holdings, history, nav-history, TWR, net-worth build/status; deprecated `/finvu/sync`).
- **services/** — `portfolio_service`, `networth/` (the net-worth series package — see below), `twr_service` (DB adapter feeding the `financial_primitives.twr_wealth_index` kernel for the Returns tab), `benchmark_service` (portfolio-vs-Nifty-50 chart), `allocation_rollup` (the SINGLE source for the Equity/Debt/Others mix — shared by the dashboard donut and chat's current-mix narration in `aa_engine`, so the two can never disagree; callers add their own cash bucket), `portfolio_query_service` (gateway to the `AI_Agents` portfolio_query agent: builds the facts pack from the agent, then answers through the shared answer formatter and applies the guardrail backstop).

## Gotchas & invariants

- **The net-worth series is NOT CAS-snapshot-scoped, and must never become so.** Its grain is `(user_id, recorded_date)` — there is no room for two values on one day, and none needed, because the whole series is recomputable from the ledger. Scoping it was an outage: a second upload stamped the old rows with the now-superseded snapshot, the read hook hid them, and users saw 3,529 rows stored and 0 visible. Test-enforced (`ingestion/tests/test_cas_scope.py`).
- **`portfolio_networth_jobs` is not scoped either.** A job belongs to a user, not a statement. Scoped, a running job vanished from every read the instant a second upload superseded its snapshot — exactly when a second upload is most likely — and `create_job` then re-raised the `IntegrityError` from the still-live partial unique index, 500ing the second upload.
- **A CAS upload replaces the series wholesale**, inside ONE transaction: delete every row for the user, then insert the recompute. Atomic, so no reader sees an empty chart and a crash leaves the previous series intact. An earlier version confined the DELETE to the active snapshot while the INSERT covered the window, which collided on `uq_user_nav_history_user_date` and killed the backfill at 98% (`services/networth/writer.py`).
- **A build already in flight is flagged to re-run, not merely joined.** Joining is right for a double tap on Rebuild and wrong for a second statement: that build is reading the CAS the upload just replaced (`supersede_requested`, `services/networth/job.py`).
- **Every sum a user reads as "net worth" pins the ACTIVE statement in its own query** — `visible_in_snapshot(...)` in `loader.load_ledger` / `load_openings`, `asof.compute_networth_as_of`, and a by-hand filter in `portfolio_service.revalue_primary_portfolio_at_latest_nav`. The CAS read hook applies the same predicate, but only when the listeners are installed AND the ContextVar is set — process-global state that a script, a scheduler or an older process can be missing, and each time it was, the total became the sum of every statement ever uploaded (Rs 60,792 held charted as Rs 15.1 crore). `build_series` resolves the snapshot itself when a caller passes none. Do not "simplify" these filters away because the hook already does it.
- **The daily refresh is ONE set-based statement for the whole fleet**, not a loop per user. It re-prices `user_scheme_position` at the latest NAV, **adds the series `anchor_value`** (the rebuild holds that anchor flat across every day — without it the trailing week stepped down by the anchor on every run) and carries `last_invested` forward — cost basis only moves when a transaction lands, and transactions only arrive via an upload, which already triggers a full rebuild. It reads the positions table rather than `mf_transactions` because the ledger is `CasScoped` and the read hook only filters ORM SELECTs, so a fleet-wide raw aggregate over it would double-count anyone who has uploaded twice. **Both its inputs are written only by a rebuild**, so a user who has never been rebuilt is invisible to the pricing pass — `_STALE_USERS` therefore also adopts users who have a series but no state row, which is the entire migration path off the old builder; without it their chart freezes on whatever that builder last wrote. Its drift tripwire compares against the active statement's holdings roll-up, never `portfolios.total_value` (not snapshot-scoped, pollutable by any unscoped writer). `rewrite_day` is the repair path (delete + re-insert one day, one transaction) behind `scripts/reprice_networth_today.py` (`services/networth/daily.py`).
- **Only the package may write `user_portfolio_nav_history`.** On 2026-09-13 a process still running the pre-package daily job rewrote today's point from the unscoped holdings roll-up minutes after the real pass — same 06:00/14:00/23:00 IST slots, an upsert that never touched `updated_at`. A row whose `total_value` equals the all-snapshots holdings sum while `updated_at` shows the package's last touch is that process, not a bug in here: find and stop it, then run the reprice script.
- **`GET /portfolio/nav-history` is read-only.** It used to self-heal the trailing edge on every dashboard load — a write on the hottest read path. Long horizons are downsampled in SQL to ~400 points, each a real stored day (`services/networth/reader.py`).
- **Resolve a holding's `nav_key` once, never `upper(isin)` in the loop.** `mf_nav_history` is ~14M rows; matching an ISIN-keyed holding with `upper(isin) = :code` is a parallel sequential scan, per fund, per rebuild (measured: plan cost 435k → 7k with `ix_mf_nav_isin_upper`) (`services/networth/loader.py`).
- Portfolio XIRR direction is driven by `transaction_type` (BUY/SWITCH_IN outflow, SELL/SWITCH_OUT inflow), NOT the amount's sign (`abs(amount)` is magnitude). A prior bug matched non-existent "REDEEM" types (`services/portfolio_query_service.py`, `_compute_portfolio_xirr`).
- **Per-fund XIRR is a separate lookup from portfolio XIRR.** `_xirr_by_scheme` reads `UserMfLatestSnapshot.xirr_pct` keyed by `scheme_code` — which IS the holding's `ticker_symbol` — and fills `Holding.xirr_pct` so chat can rank and compare individual funds. It returns `{}` on ANY failure by design: a missing XIRR must degrade one line of an answer, never fail the turn, so a broken lookup shows up as the model quietly dropping per-fund XIRR rather than as an error — check the warning log (`services/portfolio_query_service.py`).
- **`portfolio_query` is where saved preferences are READ, and it never writes them.** The agent's `preference_question` extra raises `show_preferences_pill`, so a readout ("am I still avoiding small caps?") or a wholesale clear ("reset my preferences") is answered from the stored record with a route to the preferences page attached. Chat can describe the record; only the preferences screen edits it (`services/portfolio_query_service.py`).
- **Market context is gated, and it's Prozpr's own view only.** `answer_portfolio_query` passes `want_fund_house_view` from the classifier's `ctx.tools_needed` — judgement questions ("am I too aggressive?") load the **Prozpr-only** fund-house view (our stance, **no fund house named**); unconditional loading once made the model compare an allocation % against a P/E. The factual `market_commentary` channel was dropped from portfolio entirely; the view defaults `False` (`services/portfolio_query_service.py`).
- Canonical portfolio XIRR is `mutual_funds.services.xirr_service.compute_portfolio_xirr` (what `benchmark_service` reuses). `portfolio_query_service._xirr` is a divergent hand-rolled Newton-Raphson — prefer the shared service for new portfolio code (`services/portfolio_query_service.py`).
