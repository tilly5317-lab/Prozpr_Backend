# app/domains/ingestion/ — external-data adapters: MF Central CAS, CAMS/KFintech CAS PDF, AA normalizer, SimBanks XML, (sidelined) Finvu

## Layers

- **models/** — `cas_upload.py` (the `cas_uploads` snapshot header + the `CasScoped` mixin that carries `cas_upload_id` onto the 18 stamped tables) and `mfc_cas_request.py` (one row per MF Central consent attempt). Everything else it writes lives in other domains' tables (`mutual_funds`, `portfolio`).
- **schemas/** — cams / mfc_cas / mf_aa / finvu / simbanks payloads.
- **routers/** — `/mf-ingest` (CAMS PDF upload, CAS request-by-email, AA-import normalize, mfapi.in refresh/backfill), `/mfc-cas` (MF Central consent flow), `/cas-uploads` (read-only statement history), `/simbanks`.

## Gotchas & invariants

- **Two sources produce a statement now, one pipeline consumes it.** `ingest_parsed_cas` (`services/cams_cas_ingest.py`) takes an already-parsed legacy dict and owns everything from the validity gates down — snapshot mint, scoped persist, activation. `ingest_cams_pdf` (casparser.in) and `mfc_cas_ingest.import_from_qr` (MF Central) both call it, so a new source needs an adapter to the legacy dict and nothing else. `file_bytes` is optional there: MFC delivers JSON, so there is no PDF to archive and no `user_cas_documents` row.
- **MFC uses TWO different AES setups and mixing them fails opaquely.** The API envelope hashes the shared key (`SHA-256(key)[:32]`) with a CONSTANT IV; the redirect URL uses a raw 32-byte key with a random IV and a `<iv_hex>:<data_hex>` wire format. Applying one to the other produces valid base64 that MFC rejects with a bare 422 (`services/mfc_crypto.py`).
- **The MFC signature is a DETACHED JWS, not the JWT their guide shows.** Their written docs say `jwt.sign({data}, key, RS256)`; their own Postman capture is RFC 7797 `b64:false` with an empty payload segment, signed over `header.<encrypted_request>` with the ciphertext used verbatim. The capture wins; `MFC_SIGNATURE_MODE=jwt` is the escape hatch if a tenant disagrees.
- **MFC has no transaction-type enum.** The PDF path gets PURCHASE / SWITCH_IN / …; MFC gives free-text `trxnDesc` plus a usually-empty `trxnTypeFlag`. `mfc_cas_adapter.classify_transaction` rebuilds the enum, ordered longest-intent-first (SWITCH OUT before SWITCH, SIP before PURCHASE) with the unit sign only as a tie-break — some AMCs report redemption units unsigned, so a description saying "Redemption" must outrank a positive count or a sell is ingested as a buy. Unrecognised rows become UNKNOWN, which `_TXN_TYPE_FLAG` already skips.
- **The MFC QR is single-use and the flow cannot be resumed without it.** `validateQRCode` is never retried on a business rejection — MFC invalidates the QR on the first successful exchange, and a retry burns a consent the investor has to re-give via a fresh OTP. `mfc_cas_requests` exists because `reqId`/`clientRefNo` have to survive the minutes the investor spends on MFC's site; losing either strands that consent.
- **Most `mfc_cas_requests` rows rest at `initiated` forever, and that is correct.** MFC exposes no "did they consent yet" endpoint, so an abandoned consent and one still in progress are indistinguishable. The QR arriving back is the only completion signal.
- **A Summary CAS from MFC is still rejected**, by the same `ingest_parsed_cas` gate the PDF path hits — but the flow returns 200 with the display payload and a `rejection` string, so the investor sees what they consented to alongside why it cannot rebuild a portfolio. The variant is the investor's choice inside MFC's UI, not ours.
- **MFC returns fields our schema has no home for** — per-folio `purAllow`/`redAllow`/`sipAllow`/… transactability flags, the registered bank mandate, KYC and nominee status, the demat split. `mfc_cas_adapter.summarize_for_display` surfaces them (PAN and account number masked) for the import screen only; none of it is persisted yet.
- **The consent OTP is MFC's, and there is no live API for it.** Their client surface is three calls (token, `newCasRequest`, `validateQRCode`); guide p.12: *"All OTP verification and data selection is handled by MFC's frontend."* So `Settings.mfc_otp_capture()` reports `"app"` ONLY under the mock (where `/mfc-cas/verify-otp` can forward to the mock consent site's own `/api/auth/verify-otp`) and `"mfc"` against real credentials — and the frontend renders its OTP screen off that flag, so a box that could not check a code is never shown. `MFC_OTP_CAPTURE=app` is the escape hatch for the day MFC ships one. A verified session makes the mock's consent page skip straight to the statement choice, so the investor is never asked twice.
- **`/mfc-cas/config` reports `integration_mode` (`MFC_INTEGRATION_MODE`, default `popup`).** MFC documents popup/iframe/redirect and auto-detects which is running, so the container is ours to pick; `popup` keeps it obvious that the consent page is theirs. Two traps if you switch to `iframe`: `mfc_origin` is a base URL (it carries `/mfc-mock` under the mock) and must be reduced to an origin before comparing with `event.origin`; and the referrer has to reach MFC, since they derive their `postMessage` targetOrigin from `document.referrer`, falling back to the redirect URL's origin, which is never ours.
- **The mock consent page's relative fetches are SIBLING names.** It is served at `/mfc-mock/api/auth/start`, so `'verify-otp'` is correct and `'../api/auth/verify-otp'` resolves to `/mfc-mock/api/api/auth/verify-otp` — which 404'd every OTP submit. Its OTP is a fixed `123456` (`MFC_MOCK_OTP`; set it to `uat` for MFC's real UAT rule, `00` + the PAN's last four digits, guide p.26). `/mfc-cas/start` echoes it back as `mock_otp` — null against real credentials — because the app's own OTP screen now runs BEFORE MFC's page opens, so nothing else would tell a developer what to type.

- **The MFC mock is MOUNTED, not run separately** (`dev/mfc_mock.py`, at `/mfc-mock` from `app/main.py`), so `uvicorn main:app --reload` is the only process a developer needs. `Settings.mfc_mock_enabled()` requires BOTH no real `MFC_CLIENT_ID` and a non-production `DEPLOY_ENV`, and every MFC credential resolves through `_mfc_credential` so the mock is on or off as a SET — a half-real, half-mock combination authenticates and then dies at decrypt. `/config` reports `environment: "mock"` and the flow shows a banner, so sample holdings are never mistaken for real ones. `scripts/mfc_mock_server.py` is now only a runner for the same module (pointing another backend at it). It validates our wiring, NOT MFC's real behaviour.
- **The QR comes back three ways, and only the last is guaranteed.** (1) MFC's own `mfc-cas-download` postMessage carries the image as base64 — no disk, no permission, works on mobile and in every browser; their platform-compatibility guide defines it for WebView hosts and the mock posts it to `window.opener`/`window.parent` too, which is the one extension the live service would need. (2) The Downloads-folder scan (`src/lib/downloadScan.ts`, File System Access API) — **Chromium desktop only**; Firefox and Safari have no `showDirectoryPicker` at all, so mobile never has this. (3) The `<input type=file>` picker, which is why it can never be removed. The mock downloads via a **blob URL, never `data:`** — Chrome navigates to a data: URI instead of downloading it in some window contexts, and then no file ever reaches Downloads.
- **The mock's HTML uses `__TOKEN__` substitution, not `str.format`.** The consent page carries a stylesheet and a script, and `.format` raises `KeyError` on the first CSS brace — which is exactly how the mounted mock first 500'd.
- **Every CAS upload SUPERSEDES; nothing is deleted.** Each upload mints a `cas_uploads` row and stamps everything derived from it with that id; the previous upload becomes `superseded` and the app stops reading it. Reads are filtered and writes are stamped by two session hooks in `app/core/cas_scope.py`, NOT by per-query edits. A new table holding CAS-derived state must inherit `CasScoped` (models), be added to `_ADOPT_BY_USER_ID`/`_ADOPT_BY_PORTFOLIO` (`services/cas_upload_service.py`), the DDL loop in `app/core/database.py`, and `scripts/backfill_cas_uploads.py`.
- **`cas_upload_id IS NULL` is always visible** — it means "not owned by any statement", which is how manual transactions, SimBanks/Finvu rows and not-yet-adopted legacy data stay on screen. It also means an unadopted legacy row would be counted ALONGSIDE a new statement, which is why `ingest_cams_pdf` adopts orphan rows into a legacy snapshot before minting a new one (`cas_upload_service.ensure_legacy_snapshot`).
- **The transaction fingerprint includes `cas_upload_id`** (`services/mf_aa_normalizer.py:_build_fingerprint`). Without it the ledger insert's `ON CONFLICT DO NOTHING` against `uq_mf_txn_source_fingerprint` makes the SECOND upload insert zero rows — an empty ledger reported as a large `skipped_duplicate` count. Never take the snapshot out of that hash.
- **`chat_ai_module_runs` is scoped, `chat_sessions` / `chat_messages` / `chat_session_state` are not.** A follow-up question after an upload must not be answered from a module payload priced off the replaced statement, so those runs go out of scope with it. The visible conversation and any in-flight draft state survive untouched — only the reusable computed payload is hidden.
- **Rebuild-in-place DELETEs must carry `scope_filter(...)`.** The read hook only filters SELECTs, so an unqualified "clear then rewrite" (allocations, holdings, the latest-holdings cache, the net-worth series) would delete every earlier snapshot's rows. Non-CAS ingests (SimBanks, Finvu) use `non_snapshot_filter(...)` to stay off CAS rows entirely.
- **`reset_user_financial_data` is now only the flag-off path.** `CAS_SNAPSHOT_VERSIONING=false` restores the original destructive behaviour in one env var; `replace_existing` is retained for API compatibility only and changes nothing.
- Re-uploading the byte-identical PDF that is already active returns the existing snapshot: no second (billed) casparser call, no duplicate row (`cas_upload_service.find_identical_active`).
- A failed ingest leaves the snapshot `failed` and the PREVIOUS one still active, so the user's app is untouched — unlike the old order, where the wipe ran first and a mid-ingest failure left the account empty.
- A successful CAMS upload fires a best-effort BACKGROUND net-worth backfill, gated: only if status != FAILED, txns inserted, and no job already running (idempotent); a failed kickoff never fails the upload (`routers/mf_ingest_router.py`).
- **Parsing is REMOTE** via the CAS Parser API (`api.casparser.in` `/v4/smart/parse`); the JSON is adapted back onto the legacy parsed-CAS shape (`casparser_adapter.to_legacy_parsed`) so downstream invariants hold — the old in-process `casparser`/`pymupdf` parsing is gone. The client is inert unless `CASPARSER_API_KEY` is set (`Settings.casparser_enabled()`) (`cams_cas_ingest._parse_cas_via_api`).
- CAMS ingest writes across THREE areas: raw audit (`mf_aa_imports`/summaries/transactions), normalized `mf_transactions`, and bucketed `portfolio_allocations` (Cash/Debt/Equity/Other) (`services/cams_cas_ingest.py`).
- A transaction-type allow-list (`_TXN_TYPE_FLAG`) silently SKIPS non-holding-flow rows — DIVIDEND_PAYOUT, STAMP_DUTY_TAX, STT_TAX, TDS_TAX, etc. — so only unit-moving txns become `mf_transactions` (`services/cams_cas_ingest.py`).
- CAS profile/identity back-fill FILLS BLANKS ONLY — email, PAN, address; **the investor name is NOT taken from the CAS** (the sign-up name is authoritative; the legal name is still kept in the `mf_aa_imports` audit row). Anything the user already set is never overwritten, and unique email/PAN are skipped on clash (`services/cams_cas_ingest.py`, `_backfill_user_profile`).
- `ingest_cams_pdf` REJECTS, before any DB write and before a snapshot is minted, two statement variants — raising `CamsPdfParseError` → HTTP 422: a **Summary CAS** (`cas_type == "SUMMARY"`, holdings only / no txn history) and a statement with **no current holdings** (`_total_market_value(parsed) <= 0`) (`services/cams_cas_ingest.py`).
- The normalized `mf_transactions` bulk insert is CHUNKED (1500 rows/statement) — asyncpg caps a statement at 32767 bind params and each row binds 18, so one VALUES insert breaks past ~1820 txns (a 15y+ CAS). The normalizer's user-facing `error` is a fixed friendly string; raw exceptions go to the log + `failure_reason` audit column only (`services/mf_aa_normalizer.py`, `_INSERT_CHUNK_ROWS`).
- casparser.in caps MULTIPART bodies at ~1.8 MB (plan-based, their support 2026-08-04), but their `pdf_url` mode has NO size limit — so CAS PDFs over `CASPARSER_MULTIPART_MAX_BYTES` (default 1.7 MB) are staged in the private `CAMS_STAGE_S3_BUCKET` under an unguessable key, casparser fetches a ~10-min presigned GET, and the object is deleted right after the parse (`services/cams_pdf_stage.py`; branch in `cams_cas_ingest.py`, `_parse_cas_via_api`). boto3 imports lazily; bucket unset (local dev) → multipart fallback and an explicit "statement too large" `CamsPdfParseError` on the resulting 413. Bucket needs Block Public Access ON + a 1-day lifecycle expiry on `cams-stage/` as the crash backstop.
- Successfully parsed statements are KEPT: archived to S3 under `user-cas/{user_id}/{doc_id}.pdf` + recorded in `user_cas_documents` (owned by `mutual_funds/models/user_cas_document.py`), which backs the profile's "My CAS statements" list (`GET/DELETE /mf-ingest/cas-documents`, presigned 5-min downloads). That table is NOT snapshot-scoped — it is the file archive, and it outlives the snapshot that parsed it (a snapshot points at its document via `cas_uploads.cas_document_id`). Never add it to `reset_user_financial_data`'s list either. Any bucket lifecycle expiry must be scoped to the `cams-stage/` prefix ONLY, or archived statements get deleted (`services/cams_pdf_stage.py`).
- Finvu is DEPRECATED (account-aggregator licensing), superseded by CAMS CAS upload; retained for reference, off all active paths (`services/finvu_portfolio_sync.py`).
