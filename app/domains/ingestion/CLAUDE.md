# app/domains/ingestion/ — external-data adapters: CAMS/KFintech CAS PDF, AA normalizer, SimBanks XML, (sidelined) Finvu

## Layers

- **models/** — `cas_upload.py` only: the `cas_uploads` snapshot header + the `CasScoped` mixin that carries `cas_upload_id` onto the 18 stamped tables. Everything else it writes lives in other domains' tables (`mutual_funds`, `portfolio`).
- **schemas/** — cams / mf_aa / finvu / simbanks payloads.
- **routers/** — `/mf-ingest` (CAMS PDF upload, CAS request-by-email, AA-import normalize, mfapi.in refresh/backfill), `/cas-uploads` (read-only statement history), `/simbanks`.

## Gotchas & invariants

- **Every CAS upload SUPERSEDES; nothing is deleted.** Each upload mints a `cas_uploads` row and stamps everything derived from it with that id; the previous upload becomes `superseded` and the app stops reading it. Reads are filtered and writes are stamped by two session hooks in `app/core/cas_scope.py`, NOT by per-query edits. A new table holding CAS-derived state must inherit `CasScoped` (models), be added to `_ADOPT_BY_USER_ID`/`_ADOPT_BY_PORTFOLIO` (`services/cas_upload_service.py`), the DDL loop in `app/core/database.py`, and `scripts/backfill_cas_uploads.py`.
- **`cas_upload_id IS NULL` is always visible** — it means "not owned by any statement", which is how manual transactions, SimBanks/Finvu rows and not-yet-adopted legacy data stay on screen. It also means an unadopted legacy row would be counted ALONGSIDE a new statement, which is why `ingest_cams_pdf` adopts orphan rows into a legacy snapshot before minting a new one (`cas_upload_service.ensure_legacy_snapshot`).
- **The transaction fingerprint includes `cas_upload_id`** (`services/mf_aa_normalizer.py:_build_fingerprint`). Without it the ledger insert's `ON CONFLICT DO NOTHING` against `uq_mf_txn_source_fingerprint` makes the SECOND upload insert zero rows — an empty ledger reported as a large `skipped_duplicate` count. Never take the snapshot out of that hash.
- **`chat_ai_module_runs` is scoped, `chat_sessions` / `chat_messages` / `chat_session_state` are not.** A follow-up question after an upload must not be answered from a module payload priced off the replaced statement, so those runs go out of scope with it. The visible conversation and any in-flight draft state survive untouched — only the reusable computed payload is hidden.
- **Rebuild-in-place DELETEs must carry `scope_filter(...)`.** The read hook only filters SELECTs, so an unqualified "clear then rewrite" (allocations, holdings, the latest-holdings cache, the net-worth series) would delete every earlier snapshot's rows. Non-CAS ingests (SimBanks, Finvu) use `non_snapshot_filter(...)` to stay off CAS rows entirely.
- **`reset_user_financial_data` is now only the flag-off path.** `CAS_SNAPSHOT_VERSIONING=false` restores the original destructive behaviour in one env var; `replace_existing` is retained for API compatibility only and changes nothing.
- Re-uploading the byte-identical PDF that is already active returns the existing snapshot: no second (billed) casparser call, no duplicate row (`cas_upload_service.find_identical_active`).
- A failed ingest leaves the snapshot `failed` and the PREVIOUS one still active, so the user's app is untouched — unlike the old order, where the wipe ran first and a mid-ingest failure left the account empty.
- A successful CAMS upload fires a best-effort BACKGROUND net-worth backfill, gated: only if status != FAILED, txns inserted, and no job already running (idempotent); a failed kickoff never fails the upload (`routers/mf_ingest_router.py`).
- **Parsing is REMOTE** via the CAS Parser API (`api.casparser.in` `/v4/smart/parse`); the JSON is adapted back onto the legacy parsed-CAS shape (`casparser_adapter.to_legacy_parsed`) so downstream invariants hold — the old in-process `casparser`/`pymupdf` parsing is gone. The client is inert unless `CASPARSER_API_KEY` is set (`Settings.casparser_enabled()`) (`cams_cas_ingest._parse_cas_via_api`).
- CAMS ingest writes across THREE areas: raw audit (`mf_aa_imports`/summaries/transactions), normalized `mf_transactions`, and bucketed `portfolio_allocations` (Cash/Debt/Equity/Other) (`services/cams_cas_ingest.py`).
- A transaction-type allow-list (`_TXN_TYPE_FLAG`) silently SKIPS non-holding-flow rows — DIVIDEND_PAYOUT, STAMP_DUTY_TAX, STT_TAX, TDS_TAX, etc. — so only unit-moving txns become `mf_transactions` (`services/cams_cas_ingest.py`).
- CAS profile/identity back-fill FILLS BLANKS ONLY — email, PAN, address; **the investor name is NOT taken from the CAS** (the sign-up name is authoritative; the legal name is still kept in the `mf_aa_imports` audit row). Anything the user already set is never overwritten, and unique email/PAN are skipped on clash (`services/cams_cas_ingest.py`, `_backfill_user_profile`).
- `ingest_cams_pdf` REJECTS, before any DB write and before a snapshot is minted, two statement variants — raising `CamsPdfParseError` → HTTP 422: a **Summary CAS** (`cas_type == "SUMMARY"`, holdings only / no txn history) and a statement with **no current holdings** (`_total_market_value(parsed) <= 0`) (`services/cams_cas_ingest.py`).
- The normalized `mf_transactions` bulk insert is CHUNKED (1500 rows/statement) — asyncpg caps a statement at 32767 bind params and each row binds 18, so one VALUES insert breaks past ~1820 txns (a 15y+ CAS). The normalizer's user-facing `error` is a fixed friendly string; raw exceptions go to the log + `failure_reason` audit column only (`services/mf_aa_normalizer.py`, `_INSERT_CHUNK_ROWS`).
- casparser.in caps MULTIPART bodies at ~1.8 MB (plan-based, their support 2026-08-04), but their `pdf_url` mode has NO size limit — so CAS PDFs over `CASPARSER_MULTIPART_MAX_BYTES` (default 1.7 MB) are staged in the private `CAMS_STAGE_S3_BUCKET` under an unguessable key, casparser fetches a ~10-min presigned GET, and the object is deleted right after the parse (`services/cams_pdf_stage.py`; branch in `cams_cas_ingest.py`, `_parse_cas_via_api`). boto3 imports lazily; bucket unset (local dev) → multipart fallback and an explicit "statement too large" `CamsPdfParseError` on the resulting 413. Bucket needs Block Public Access ON + a 1-day lifecycle expiry on `cams-stage/` as the crash backstop.
- Successfully parsed statements are KEPT: archived to S3 under `user-cas/{user_id}/{doc_id}.pdf` + recorded in `user_cas_documents` (owned by `mutual_funds/models/user_cas_document.py`), which backs the profile's "My CAS statements" list (`GET/DELETE /mf-ingest/cas-documents`, presigned 5-min downloads). That table is NOT snapshot-scoped — it is the file archive, and it outlives the snapshot that parsed it (a snapshot points at its document via `cas_uploads.cas_document_id`). Never add it to `reset_user_financial_data`'s list either. Any bucket lifecycle expiry must be scoped to the `cams-stage/` prefix ONLY, or archived statements get deleted (`services/cams_pdf_stage.py`).
- Finvu is DEPRECATED (account-aggregator licensing), superseded by CAMS CAS upload; retained for reference, off all active paths (`services/finvu_portfolio_sync.py`).
